# Дизайн-спека: Ежедневник (tweek.so-style)

**Дата:** 2026-07-07
**Статус:** Утверждается
**Ссылка-референс:** https://tweek.so/

---

## 1. Назначение и цель

Кроссплатформенный ежедневник в стиле tweek.so: минималистичный планировщик задач, организованный вокруг **недели** (а не почасовых слотов). Local-first: данные хранятся локально, синхронизация между устройствами — безсерверная, через Google Drive.

**Цель Фазы 1 (MVP):** работающее, красивое приложение на Android и десктопе с локальным хранением, без синхронизации. Синхронизация/CRDT/коллаборация добавляются позже отдельными фазами.

## 2. Обоснование выбора стека

> **⚠️ Ревизия 2026-07-14:** Изначально выбран Flutter + Drift + Rust(FFI). После
> реализации MVP (Фаза 1, части 1–3, 18 коммитов, архив в git-теге
> `flutter-archive-mvp`) и попытки macOS-сборки выяснилось: Flutter требует
> полный Xcode (20 ГБ). Переоценив анализ, признаём первоначальное решение
> ошибочным — **Tauri v2 + Rust + React/SolidJS** (оригинальный замысел автора)
> лучше соответствует проекту: Rust-ядро нативно (без FFI-моста), macOS-сборка
> на CLT (без полного Xcode), web-версия бесплатно для Фазы 4 (шаринг). Аргумент
> «Flutter лучше для тач-dnd» реален, но не перевешивает потерю Rust-нативности.

### Финальный рейтинг (с пересмотром)

| Место | Стек | Балл | Вердикт |
|---|---|---|---|
| 🥇 1 | **Tauri v2 + Rust + React/SolidJS** | **68/80** | **ВЫБРАНО (пересмотр)** |
| 2 | Flutter + Drift + Rust(FFI) | 67/80 | Реализован MVP, но требует Xcode; FFI-мост — доп. слой боли для Rust-ядра |
| 3 | React Native (Expo) + WatermelonDB | 63/80 | Local-first-козырь отпадает (требуют бэкенд); desktop слаб |
| 4 | Flutter + Drift (без Rust) | 62/80 | Упрощённый вариант |
| 5 | Capacitor + React | 55/80 | WebView-проблемы на тач, нет Rust-ядра |

### Почему Tauri v2 + Rust + React/SolidJS (пересмотр)

1. **Rust-ядро нативно:** Tauri — это Rust-приложение с WebView-фронтом. Бэкенд
   на Rust «из коробки», без FFI-моста (`flutter_rust_bridge`). CRDT, AES-256,
   merge-логика Фазы 3 реализуются прямо в Rust-командах Tauri.
2. **macOS-сборка без полного Xcode:** достаточно Command Line Tools (CLT уже
   есть) + системный WebKit. Flutter требует 20 ГБ Xcode.
3. **Соответствие оригинальному плану автора:** стек совпадает с изначальным
   замыслом (Tauri v2 + Rust Core + React/SolidJS).
4. **Web-версия бесплатно для Фазы 4:** Tauri-фронт — это web tech, публичный
   шаринг календаря (read-only) строится из той же кодовой базы.
5. **Drag-and-drop на desktop идеален:** `@dnd-kit/core` в WebView на macOS/Windows
   даёт плавный 60fps dnd. (На тач-Android dnd в WebView слабее — принятый компромисс.)

## 3. Архитектура

```
┌─────────────────────────────────────────────────┐
│  Frontend: React/SolidJS + TypeScript           │
│  (рендерится в Tauri WebView, системный WebKit) │
│  • Виды: День / Неделя / Месяц                  │
│  • Drag-and-drop (@dnd-kit/core)                │
│  • Мини-календарь с индикатором занятости       │
│  • Сеты цветов, темы                            │
│  • Тонкий клиент: state через Tauri IPC         │
└────────────────────┬────────────────────────────┘
                     │ Tauri IPC (invoke / events)
┌────────────────────▼────────────────────────────┐
│  Rust Core (Tauri backend — нативно, без FFI)   │
│  • rusqlite / sqlx: локальная SQLite (ACID)     │
│  • Команды: get_tasks, upsert_task, move_task   │
│  • automerge-rs: CRDT-merge [Фаза 3]            │
│  • AES-256-GCM: шифрование снапшотов [Фаза 3]   │
└────────────────────┬────────────────────────────┘
                     │ REST [Фаза 3]
┌────────────────────▼────────────────────────────┐
│  Transport: Google Drive appDataFolder          │
│  • Скрытая папка, без своего сервера            │
└─────────────────────────────────────────────────┘
```

**Принцип изоляции:** Frontend (React) — тонкий клиент, общается с Rust-ядром
только через Tauri IPC-команды. Локальная SQLite живёт в Rust, что даёт ACID
и микросекундную latency без JS-движка. Слой синхронизации (Фаза 3) добавляется
в Rust-ядро без переделок UI.

## 4. Дорожная карта (фазы)

> **Стек после пересмотра 2026-07-14:** Tauri v2 + Rust + React/TypeScript.

### Фаза 1 — Локальный MVP (ядро) 🎯 текущий фокус
- Виды: **День / Неделя / Месяц** + сегментированный переключатель
- **Inline-ввод задач прямо в поле дня** (как tweek.so): печатай в строке дня →
  Enter → задача создана. Никаких модалок/FAB для быстрого создания.
- Мини-календарь с индикатором занятости (точки/полоски/свободен/прошло)
- Создание/редактирование/удаление задач (inline + опции в карточке)
- **Drag-and-drop** задач между днями (@dnd-kit/core)
- **Сеты цветов** (палитра; цвет выбирается на карточке — категория НЕ навязывается при создании)
- **Экран настроек**: тема, первый день недели, авто-перенос вкл/выкл
- **Выбор дат** (date picker) для прыжка к произвольному дню
- **Авто-перенос** невыполненных задач на завтра (Automate)
- **Темы**: минимум paper-white, тёмная, холодная
- Локальная SQLite (rusqlite в Rust-ядре), полностью офлайн

### Фаза 2 — Богатые задачи
- Подзадачи (subtasks)
- Заметки и вложения (файлы/изображения) к задаче
- Повторяющиеся задачи (день/неделя/месяц/год/кастом)
- Напоминания (локальные push-уведомления)
- Поиск с фильтром по цвету-сету

### Фаза 3 — Синхронизация (Rust-ядро)
- **automerge-rs** CRDT (нативно в Rust, без FFI-моста)
- Шифрование AES-256-GCM снапшотов
- Google Drive `appDataFolder` (безсерверная синхра)
- Разрешение конфликтов без потерь

### Фаза 4 — Коллаборация и интеграции
- Шаринг календаря по ссылке (web-публикация, read-only)
- Несколько календарей (личный/рабочий/семейный)
- Синхронизация с Google Calendar / Apple Calendar
- Real-time коллаборация (опционально, может потребовать relay)

### Фаза 5 — Полировка
- iOS, web, desktop-сборки (полное покрытие)
- Экспорт/импорт
- Виджеты, Siri-интеграция (опционально)

## 5. Модель аккаунтов / идентичности

**Решение: Без аккаунтов (device UUID) + опциональный Google позже.**

| Вариант | Балл | Вердикт |
|---|---|---|
| **B. Без аккаунтов (device UUID)** | **42/50** | **ВЫБРАНО** |
| A. Только Google-аккаунт | 37/50 | Слишком рано привязывать к Google |
| C. Свой бэкенд с аккаунтами | 18/50 | Ломает local-first архитектуру |

**Реализация:**
- Локальный UUID устройства генерируется при первом запуске, хранится в `flutter_secure_storage`.
- `device_uuid` = `actor_id` для CRDT (каждая реплика = устройство).
- Синхронизация подключается опционально (Фаза 3): юзер привязывает любой Google-аккаунт **только как транспорт** (Drive-хранилище), а не как идентификатор пользователя.
- Шаринг (Фаза 4) — через публичный токен ссылки, без аккаунтов.
- Никакой email-регистрации, никакой телеметрии по умолчанию. Данные шифруются (AES-256) перед отправкой в Drive.

## 6. Модель данных

### Решение по модели задачи: **Тощая в MVP** (обоснование ниже).

**Почему тощая, а не богатая «на вырост»:**
- CRDT (automerge) синхронизирует изменения документов, не реляционные таблицы. Каждое лишнее поле «на вырост» = вечный мёртвый вес в каждом снапшоте + усложнение merge-логики.
- Drift (SQLite) делает локальные миграции тривиальными — это НЕ аргумент за богатую схему. Боль начинается на уровне CRDT/синхры.
- Принцип YAGNI: начинать минимально, наращивать осознанно.

### Схема БД (Фаза 1, Drift/SQLite)

**`tasks`**
| Поле | Тип | Описание |
|---|---|---|
| id | TEXT (UUID) | CRDT-стабильный идентификатор, PK |
| title | TEXT | Текст задачи |
| date | INTEGER (epoch day) | День привязки (LocalDate) |
| is_done | INTEGER (bool) | Выполнено |
| color_set_id | TEXT (UUID?) | Ссылка на сет цветов (null = «без категории») |
| sort_order | REAL | Для ручной сортировки/drag-and-drop |
| created_at | INTEGER (epoch ms) | Время создания |
| updated_at | INTEGER (epoch ms) | Время последнего изменения |
| device_id | TEXT (UUID) | Чьё изменение (для CRDT actor) |

**`color_sets`**
| Поле | Тип | Описание |
|---|---|---|
| id | TEXT (UUID) | PK |
| name | TEXT | Название сета («Работа», «Личное») |
| color | INTEGER | ARGB-цвет |
| sort_order | REAL | Порядок в палитре |

**`settings`** (key-value)
| Поле | Тип | Описание |
|---|---|---|
| key | TEXT | PK (напр. `theme`, `default_view`, `week_start`) |
| value | TEXT | Сериализованное значение |

**Дефолтные сеты цветов** (создаются при первом запуске): Без категории (бежевый), Работа (терракотовый), Личное (бирюзовый), Спорт (коралловый).

## 7. UI / UX дизайн

### Навигация
- **Нижняя панель** (mobile) / **боковая** (desktop): **Календарь** (главный экран) · **Поиск** (Фаза 2) · **Настройки**.
- Тап по дате в мини-календаре → прыжок в этот день/неделю.

### Главный экран
- **Шапка:** название приложения · **сегментированный переключатель День/Неделя/Месяц** · поиск · настройки.
- **Мини-календарь** (sidebar на десктопе, сворачивается в шапку на телефоне):
  - Каждая ячейка дня показывает индикатор занятости.
  - **3 уровня:** 1–2 точки = немного задач; цветная полоска = загруженный день (3+); серая заливка = прошедший; пустая ячейка = свободен.
  - Точки окрашены в цвет сета доминирующих задач.
  - Тап по дню → прыжок.

### Вид «Неделя» (по умолчанию)
- **7 колонок горизонтально** (tweek-стиль): колонка = день, карточки = задачи.
- Цвет карточки = цвет сета.
- Выполненные задачи — зачёркнуты, приглушены.
- Сегодняшний день — подсвечен акцентной рамкой.
- **Drag-and-drop** карточки между колонками = перенос задачи на другой день.
- **Адаптивность (Фаза 1):** на телефоне в портрете неделя показывается **вертикальным списком дней** (дни сверху вниз, задачи свёрнуты); на планшете/десктопе — **горизонтально 7 колонок**. Пользователь может вручную переключать горизонтальный/вертикальный режим в Настройках независимо от устройства. Оба режима входят в Фазу 1.

### Вид «Месяц»
- Классическая сетка месяца с превью первых 2–3 задач в каждой ячейке (текстом) + точки для остальных.

### Вид «День»
- Одна колонка, все задачи дня списком, крупный шрифт, фокус.

### Карточка задачи
- Минимум в MVP: чекбокс выполнено · цветной маркер сета · текст.
- Тап → inline-редактирование标题а.
- Свайп влево → удалить; удержание → выбрать сет/перенести.

### Авто-перенос (Automate)
- При открытии приложения в новый день: все невыполненные задачи прошлых дней переносятся на сегодня (с уведомлением-плашкой «Перенесено N задач»).
- Поведение настраивается в Настройках (вкл/выкл).

### Темы (Фаза 1 минимум)
- **Paper-white** (по умолчанию, бежевый фон #faf7f0, как tweek).
- **Тёмная** (тёплый чёрный, не чисто-серый).
- **Холодная** (приглушённый синий).
- Акцентный цвет: терракотовый #c9a87c.

## 9. Обработка ошибок

- **БД:** все операции через транзакции Drift; при ошибке — откат, UI показывает snackbar «Не удалось сохранить».
- **Drag-and-drop:** анимация возврата карточки на исходное место при ошибке сохранения.
- **Авто-перенос:** выполняется в одной транзакции; при сбое — без изменений, повтор на следующем запуске.
- **Синхра (Фаза 3):** при обрыве соединения — локальная копия нетронута, повтор push/pull на следующем запуске. CRDT гарантирует консистентность после повторного merge.
- **Валидация:** пустой title не сохраняется (inline-ошибка); дата в прошлом разрешена (для бэклога).

## 10. Тестирование

| Уровень | Что покрываем | Инструмент |
|---|---|---|
| Unit | Drift-запросы, логика авто-переноса, сортировки, вычисление занятости для календаря | `flutter_test` |
| Widget | Виды День/Неделя/Месяц, переключатель, drag-and-drop, карточка задачи, мини-календарь | `flutter_test` |
| Интеграционные | Сценарий: создать → перетащить → отметить → проверить авто-перенос | `integration_test` |
| Rust-ядро (Фаза 3) | CRDT-merge двух реплик, крипто round-trip, сериализация | `cargo test` |

**Критические сценарии MVP:**
1. Создать задачу сегодня → видна в неделе и мини-календаре.
2. Перетащить задачу на завтра → дата обновилась.
3. Отметить выполненной → зачёркнута, цвет приглушён.
4. Не выполнить вчера → при открытии сегодня авто-перенесена.
5. Переключить Неделя→Месяц→День → данные консистентны во всех видах.
6. Сменить тему → применяется мгновенно ко всем экранам.
