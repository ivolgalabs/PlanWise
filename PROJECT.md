# PlanWise (daily-planner)
**Current state:** `28f7ad5` 15.10.2026 · check: not recorded (line seeded 17.10.2026)
Task planner: Tauri v2 + React 19 + TypeScript + zustand + SQLite (rusqlite) + @dnd-kit.
Platforms: macOS (WidgetKit widget), Android (AlarmManager/Kotlin widgets). Web mode (browser, localStorage backend in `src/api.ts: browserApi`) — for development without Tauri.
Current version: 0.2.4. Release notes of every version — `docs/HISTORY.md`.

## Structure

- `src/` — frontend: `App.tsx` (root, reloads all tasks after every change), `store.ts` (zustand+persist, UI settings), `api.ts` (invoke wrappers + browser backend), `drag.tsx` (shared DndContext), `views/` (Day/Week/Month), `components/` (TaskCard, MiniCalendar, RightPanel, …).
- `src-tauri/src/` — `commands.rs` (commands + widget writes), `notify.rs` (notification scheduler: desktop — polling with adaptive sleep, Android — OS scheduling), `db.rs` (SQLite, WAL).
- `src-tauri/widgets/` — macOS WidgetKit extension; `scripts/bundle-macos.sh` — full build with .appex embedding.
- `legacy/` — old Flutter project (not involved).

## Commands

- Dev (web): `npm run dev` (browser backend, StrictMode double-render).
- Frontend build: `npm run build` (tsc + vite).
- Release macOS: `npm run build:macos` (= `scripts/bundle-macos.sh`: cargo tauri build + widget + signing).
- Android APK: `cd src-tauri && npx tauri android build --apk` (universal in gen/android/app/build/outputs/apk/universal/release/).
- Rust tests: `cd src-tauri && cargo test --lib notify::`.
- Android-only Rust check (cfg(target_os="android") code): with `B=$NDK/toolchains/llvm/prebuilt/darwin-x86_64/bin` — `PATH="$B:$PATH" CC_aarch64_linux_android="$B/aarch64-linux-android24-clang" AR_aarch64_linux_android="$B/llvm-ar" cargo check --target aarch64-linux-android` (without CC/AR cc-rs fails on sqlite3.c).
- Rust static analysis: `cargo fmt && cargo clippy --fix --allow-dirty && cargo check`.

## Key decisions

- **Data changes**: any action → `reload()` in App (full task reload via 3 requests) → `write_widget_data` via 600 ms debounce (see `scheduleWidgetWrite` in App.tsx) + auto-export `autoSync.ts` (2 s debounce, if enabled).
- **Auto-sync** (`src/autoSync.ts`): file `daily-planner-sync.json` in the configured folder — full backup on data change + check once a minute (last-write-wins). The commands `sync_export`/`sync_import` take the FOLDER only (Rust joins the fixed file name, so a webview cannot pass a path), do the whole read/export/import in Rust (JS keeps only timers; no multi-MB JSON over IPC) and write atomically (tmp+rename); the backup carries `contentHash`, and `sync_export` keeps the last (folder, hash) so unchanged content is not rewritten; auto-import is skipped while an export is pending or debounced (it would replace the DB and lose the edit), and the export is scheduled from mutations only (`onMutation` in App — never from `reload()`, because auto-import also reloads and would ping-pong backups between devices). Unavailable on Android (content://), manual export there.
- **App exit**: on macOS closing the last window does NOT terminate the process (run loop in lib.rs: Dock click → `Reopen` restores the window). On Android BACK now MINIMIZES (`minimize_app` → Kotlin `moveTaskToBack` via the "widget" plugin bridge; v0.1.15): the process stays alive, so the next launcher launch is warm — no cold white screen. Full exit — the "Exit" button in settings (`exit_app`). (Before 0.1.15 BACK killed the process via exit_app — every launch was cold, ~0.5–1.5 s of the themed background before WebView paints; users read it as a "white screen on every start".)
- **Scheduler** (`notify.rs`): tick → sleep until the nearest event (reminder due/digest/midnight), cap 30 min; `wake_scheduler()` wakes on settings changes and on every mutating command (task edits no longer wait for the frontend's debounced widget write). Android — fixed 60 s sync-model loop; the store write goes through the Kotlin bridge `WidgetPushPlugin.persistScheduled` (see the pitfall below), and the digest is one one-shot `At` OS alarm per day for the next 14 days (`DIGEST_DAYS`, own id per day `digest_id`, own task list; restored after reboot). Exact alarms — SCHEDULE_EXACT_ALARM + USE_EXACT_ALARM in AndroidManifest (otherwise the plugin sets inexact ones, notifications get delayed). Per-task reminder "before departure" (`travelNotifyMinutes`): "time to get ready" N minutes before departure (= start − `travelTime`), earlier than "time to leave".
- **TaskCard memoized** (React.memo + `taskEquals` by fields): after reload all task objects are new, reference comparison is always false.
- **Time conflicts**: the `conflictId` selector returns a primitive (id|null) — subscribing to the whole `s.tasks` would re-render all cards.
- **Notification → task card (deep-link)**: a reminder carries `taskId` via `.extra("taskId", …)`; the frontend listens to the plugin's `actionPerformed` at module scope (catches cold start) → `focusTaskId` → a global `AddTaskModal`. Cold-start splash — themed `windowBackground` `#f4f5f7`/`#121316`. Android reminders use `large_body` (BigTextStyle) so the full text is visible expanded.
- **ErrorBoundary** around `App` (`main.tsx`): any unhandled render error shows a visible error + reload button instead of a silent white screen. On the device the white screen is NOT reproduced (launcher/fresh-install/notification-intent launch all load fine) — likely a data- or WebView-version-specific render crash; the boundary surfaces its cause.
- **Someday plan groups**: the section is split into collapsible "Someday" / "Within a week" / "Within a month" by the soft deadline `dueEpochDay` (no separate task types). Plan-tasks are ALSO shown in the week/month grid on their deadline day (`tasksForDay` matches `dueEpochDay` for someday tasks). Protection from desync: `move_task` keeps a someday task as a plan-task (updates `due_epoch_day`), `set_someday` clears it — so dragging/editing a plan-task in the grid does NOT turn it into a day task.
- **Honest data (V15, 19.10.2026)**: `done_at`/`dropped_at` are owned by DB triggers (any writer toggling `is_done` — commands, import, Kotlin widgets — keeps them right; `write_task` ON CONFLICT never overwrites them). "Dropped" = `is_done=1` + `dropped_at`, so widgets/notify/overlap treat it as closed without a status column. `postpone_count` grows only in `move_task` (open task, date ≤ today → future); modal date edits don't count. Table `days` (note, closed_at) rides in backups. Commands `drop_task`, `get_days`, `upsert_day`. Settings persist v2: `archiveEnabled`/`autoDonePastTime` forced off — tails stay on their days.

## Pitfalls (verified by measurements 15.08)

- **dnd-kit sensors**: option literals in render break `useSensor` memoization → `activators` → internalContext is recreated → RE-RENDER OF ALL useDraggable/useDroppable on any store change. Options — module-level constants (`drag.tsx`), DndContext callbacks — useCallback.
- **zustand selectors**: a selector returning an array/object without shallow — infinite loop/excess renders; return a primitive.
- Vite caches node_modules: library patches require `vite dev --force`.
- APFS case-insensitive; Rust builds — into the shared `/Volumes/Kingston/My_projects/.cache/target` (see `~/My Project/Rust_Workspace/ARCHITECTURE.md`), there must be no local target/.
- **Android build**: gradle cache `~/.gradle/caches/8.14.3` can corrupt on abrupt interruptions (metadata.bin kotlin-dsl) — reset with `rm -rf` of the directory. libsqlite3-sys requires NDK clang in PATH: `export PATH="$HOME/Library/Android/sdk/ndk/*/toolchains/llvm/prebuilt/darwin-x86_64/bin:$PATH"` before `tauri android build` (otherwise "sccache: cannot find binary path"). gradlew does not work directly (the rust task waits for a WebSocket from the tauri CLI).
- **Android build under memory pressure**: the gradle daemon dies ("daemon disappeared", corrupted kotlin-dsl metadata) when RAM is low — this is NOT the cache. Fix: free memory (close Android Studio — it holds a lock on gen/android!), temporarily add to `gradle.properties` `org.gradle.workers.max=1` + `kotlin.compiler.execution.strategy=in-process`; revert after the build. The universal build (4 ABIs) is finicky — `--target aarch64` is enough for a phone.
- **Widget actions while the process is dead**: "done" from a widget cancels the task's reminder alarms in Kotlin (`WidgetData.cancelTaskAlarms`, ids from `files/notify-tasks.json`, which the Rust sync writes); un-done does not re-arm them, and a timed task quick-added from the widget gets no reminder — both wait for the next app launch (sync tick).
- **i18n**: `ru` (type source) and `en` (fallback) are in the main chunk; other locales are lazy (`src/locales/*.ts`, `loadLang` before the first render in `main.tsx` and in `setLang`). A new key goes into every locale file (tsc enforces it via `Dict`).
- **Force-stop on Android cancels all alarms** (including At notifications) — OS protection, not a bug: swipe from recents is safe, force-stop from settings is not.
- **Plan-group containers ("Someday"/"Week"/"Month")**: don't use `flex: 1 1 0` on them — in a short panel three expanded groups each collapse to 0 height and their headers overlap. Each group `flex: 0 0 auto` (natural height), the whole column scrolls.
- **Android 12+ cold-start splash**: `windowSplashScreenBackground` defaults to WHITE and flashes before the themed window (esp. in dark theme). Set splash bg + icon bg in `values/themes.xml` and `values-night/themes.xml` (`tools:targetApi="s"`).
- **Android WebView still flashed light over the dark window**: `tauri.conf.json` `backgroundColor` is a STATIC color (Wry `main_pipe.rs` sets it as the WebView bg regardless of theme) — in dark mode it flashed `#f4f5f7`. Fix: `src-tauri/tauri.android.conf.json` overrides `app.windows[].backgroundColor` → `#00000000` (WebView transparent; the themed `windowBackground` shows through). Desktop keeps `#f4f5f7` from the base config. Note: android/platform config `merge` uses `json_patch::merge` — arrays (e.g. `app.windows`) are REPLACED, so repeat the full window object.
- The shared target dir `/Volumes/Kingston/My_projects/.cache/target/release` may disappear (background cleanups/other projects) — rebuild before distributing artifacts.
- **Startup budget (`setup` runs BEFORE the first frame)**: any synchronous FS sweep/DB query there delays the window. Orphan sweep `cleanup_orphan_attachments` — background (`spawn_blocking`) + ONE `SELECT stored_name` (not a COUNT per file) + the DB mutex is not held during the directory walk. Measured cold start (Pixel 7 Pro, `am start -W`, 0.1.14): 545–587 ms to the first frame, unchanged vs 0.1.13 (534–565 ms) — the remaining ~550 ms is process + Tauri/wry init + WebView creation — not app code; the frontend has no data gate (shell renders immediately, lazy Month/Search chunks, 396 KB bundle). Don't re-investigate startup without a new measurement.
- **«Не запускается с 1-го раза» (Android)**: does not reproduce over adb (10 cold starts ok, no crashes/ANR in dropbox or the crash buffer). The ring diagnostics journal carries stage marks: `старт <версия>`, `start: setup done`, `start: tasks-loaded` (the `startup_milestone` command) — on the next complaint the journal tells «процесс не поднялся» (no `старт`) from «завис на этапе» (entries stop). Reading the journal from a device: a release build is not debuggable — a pulled file or a debuggable build is needed. A `hardened_malloc: madvise failure` record in the crash buffer after a force-stop is teardown noise from the WebView sandbox process, not an app failure.

## Audit batch 22.09 — pitfalls worth keeping (found by the deep audit)

- **The Android digest is pre-armed for tomorrow at the current-hour boundary.** While that alarm is pending, `pending_ids` contains the digest id, so a guard on `pending_ids` alone freezes the content: tasks added in the evening were missing from the next morning's digest (found in the 22.09 audit, fixed in 0.1.16). The sync tick now fingerprints the target day (epoch-day + task lines, `digest_fingerprint`) and re-arms only when the fingerprint changes — `digest_action` is pure and unit-tested on the desktop (the production path is Android-only, so it cannot be exercised there). In 0.1.17 the alarm itself became a repeating `Schedule::Interval` ("every day at the hour"): a one-shot `At` died after its fire or a process kill — nothing re-armed the next day until the app was opened again, and the digest went silent for days (the 30.09 complaint "8:00 notifications don't arrive"). In 0.2.5 it went back to `At` — one per day, 14 days ahead: the plugin re-arms an Interval with `setExact(RTC)` (non-wakeup, not allow-while-idle), so from day 2 the digest fired only when the phone woke; the Interval also kept the arm-time text, `show()` dismisses a visible notification with the same id (one shared id wiped today's digest when tomorrow's was armed), and the fingerprint lacked the hour.
- **`tauri-plugin-notification` 2.3.3: `show()` sets an alarm but never persists it, and `pending()` is the WRONG API for scheduled alarms.** Facts verified on a Pixel 7 Pro (Android 17) on 23.09.2026 — every one of them bit us: (1) the plugin's store (`NOTIFICATION_STORE`) is written only by `batch`, and its value is `Notification.sourceJson`, which is NEVER assigned (the Kotlin field is only read, Rust never sends it) — so the upstream store holds the string "null", `LocalNotificationRestoreReceiver` restores nothing and all alarms vanish on reboot; (2) `pending()` calls the Kotlin `getPending`, which returns `NotificationManager.activeNotifications` — notifications ALREADY in the shade, not scheduled alarms, so it is always empty before the first fire; (3) the stored string is parsed by jackson into the Kotlin `Notification`, which fails on any unknown field, cannot deserialize `extra` (a `JSObject`), and parses `schedule.at.date` with `SimpleDateFormat` pattern `yyyy-MM-dd'T'HH:mm:ss.SSS'Z'` in UTC — without the milliseconds the entry is dropped silently; (4) `Invoke.resolveObject` runs jackson over the value, and a `JSArray` comes back as `{}`, not as a JSON array (`invalid type: map, expected a sequence`). What we do instead: the alarm stays on the plugin's `show()`, while Rust builds the store JSON itself (`notify::scheduled_json`, jackson-compatible, no `extra`, date from `js_date_utc`) and the bridge `WidgetPushPlugin.persistScheduled` writes it under the notification id; the sync loop reads the list of scheduled alarms back with the bridge `scheduledIds` (a plain `ArrayList<Int>`) instead of `pending()`. Because `extra` is dropped, a reminder restored after a reboot has no `taskId` (the tap opens the app, not the task) until the next app launch re-schedules it. Verified: the digest fires in the configured hour, a reminder fires with the app backgrounded, an alarm whose day became empty is cancelled within a tick, and the digest alarm is re-armed after a reboot by `LocalNotificationRestoreReceiver` alone (process started for the broadcast, no activity). Guard: `persisted_json_matches_plugin_fields` + `js_date_is_plugin_format` tests pin the field set, the absence of `extra` and the date format — all three cost a build+device cycle to find. Two more facts from the 30.09 session: (5) the Interval variant works only with the DOUBLE-nested shape `schedule.interval.interval` (variant key → `DateMatch` hour/minute) — the plugin's `NotificationScheduleDeserializer` maps `schedule.interval` to the Kotlin `Interval` class whose `interval: DateMatch` property is the nested object, and after each fire the publisher re-arms it via `CRON_KEY`/`nextTrigger` (a one-shot `At` entry is deleted instead); (6) the Rust `show()` returns `Result` — swallowing it while writing the store entry leaves a phantom "armed" digest that the sync never retries (`let _ = show()` cost us silent mornings; the store write now happens only after a successful `show()`).
- **`capabilities` are split by platform.** Desktop `default.json` has NO fs permissions: with `fs:write-files` + `fs:scope $HOME/**` an XSS'd webview could read/overwrite any file in the home directory. Android `mobile.json` keeps them (content:// URIs from system dialogs, which `std::fs` cannot handle). Desktop manual export/import runs in Rust (`export_backup`/`import_backup`: dialog + atomic write on the Rust side); SettingsPanel keeps the plugin-fs path only under `isAndroid()`.
- **DST in `to_local`**: never fall back to reinterpreting a local time as UTC — it shifted the alarm by the whole zone offset while the desktop window compares naive wall clocks (they disagreed by hours). Ambiguous times → earliest interpretation; gap times → shift an hour back.
- **Sync/import hygiene**: `read_sync_file` returns `Result<Option<String>, String>` — a read error (revoked folder) must stay distinguishable from "file absent", otherwise auto-import dies silently; imported attachment names are validated as `base.ext` (dot-only names like `..` used to reach the parent directory); files written during an import are removed if the transaction fails.
